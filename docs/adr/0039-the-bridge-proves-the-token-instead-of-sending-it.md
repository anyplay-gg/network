# The bridge and the net service prove the token to each other instead of sending it

The launcher gives each game start a random token (`ANYPS5_NET_TOKEN`) and the net service listens on a loopback port (`ANYPS5_NET_ENDPOINT`). Until protocol version 0 the bridge opened its connection by sending that token, raw, in `hello`. Anything on the PC that can watch loopback traffic, or that sits where the bridge connects, could read the token and use it. And the bridge had no way to tell the real net service from another process that had taken the port: it handed the token to whoever answered.

Version 1 replaces the raw token with a mutual challenge. Each side contributes a fresh 32-byte random nonce, and each proves that it knows the token with an HMAC-SHA-256 keyed with the token over a fixed context string, its role and both nonces. The exchange is `hello` (the bridge's nonce), `challenge` (the service's nonce and its proof), `auth` (the bridge's proof), then `welcome` or `reject`. The bridge checks the service's proof before it sends its own, so it never answers a process that does not know the token. The token is never on the wire. The proofs are compared in constant time. The [bridge protocol](../../spec/bridge-protocol.md#authentication) has the exact bytes and test vectors, which the net service and the bridge both check.

Three limits go with it. Until the handshake is done a frame carries at most 1024 bytes ([network#111](https://github.com/anyplaynet/network/pull/111) set the cap for hello; it now covers all three handshake frames), the whole handshake has 5 seconds, and a connection that breaks the framing, sends the wrong frame or sends a proof that does not match is closed (with a reject and a reason when the sender is told something it can use, without a word otherwise).

## Considered options

- **Keep the raw token, loopback only.** The net service already accepts loopback connections only. That keeps a remote machine out and does nothing about a local process that listens in, connects first, or takes the port. A local process is the realistic adversary on a PC that runs games, a launcher and everything else.
- **A hash of the token instead of the token.** The hash would be the secret and be replayable. A fresh nonce from the other side is what makes a proof good for one connection only.
- **Only the bridge proves, the service does not.** The service would send a nonce and the bridge would answer with an HMAC over it. A squatter on the port would still get nothing it can reuse, but the bridge could not tell it from the real service and would go on to send it the game's sign-in state requests and web API calls. Both sides proving, each over both nonces and with its role in the message, authenticates the service to the bridge too, and a reflected proof does not verify.
- **TLS with a pinned key, or a Noise handshake.** Stronger and heavier. It needs a TLS or Noise library in the engine, which has none, for a channel between two processes on one PC whose payload (game traffic) is plain loopback traffic anyway. An HMAC is a hundred lines in the engine and fully testable with fixed vectors. The handshake leaves the channel itself unencrypted on purpose; this decision is about who may speak on it.
- **An `auth` message folded into `hello` with a one-flight proof of a timestamp.** It needs clocks that agree and a replay window. Nonces from both sides need neither.
- **Negotiating down to version 0.** An old bridge would keep sending the raw token, which is the very thing removed. A clean version bump with a clear reject is better: the launcher ships a net service and an AnyPS5 build that match.
- **A dependency for SHA-256 and HMAC in `bridge-protocol`.** The crate has no dependencies and is the reference for a C++ implementation of the same file; both implement SHA-256 and HMAC in a screenful of code and check them against the published vectors (FIPS 180 examples, RFC 4231) and the specification's vectors.

## Consequences

- The protocol version is 1. `hello` carries a nonce instead of the token. `challenge` (`0x0004`) and `auth` (`0x0005`) are new. A bridge of version 0 meets a reject that names both versions and says to update. A bridge of version 1 meets a net service of version 0 as a reject that says the token does not match, and that service sees a random nonce, not a secret.
- The fork's bridge must change with this: it takes the token as a key, makes a nonce from the system's random source, verifies the service's proof and sends its own. A net service of version 1 and a build of AnyPS5 of version 0 do not work together, and the launcher has to move its net service and its toolkit build in one step. The launcher's `network.ref` for this change must point at a commit whose AnyPS5 build is already offered.
- The net service now runs the handshake in the connection's own task, with the token handed to the listener through a small shared holder that the service sets when a game starts and clears when it ends. The service sees a bridge only after it has proved the token, and a bridge that proved an old token while another game start began is turned away.
- `fake-game` does the real handshake, so every test that connects a fake game exercises it. A fuzz target covers the bytes read before the handshake is done and the proof comparison.
- Not changed: game datagrams and streams between the bridge and the net service. The stream key from `welcome` still opens a stream, and loopback UDP ports are still bound by the bridge. A process that has the token (the game's own, read from its environment) is as trusted as before.
