# Discord's Social SDK runs in the net service, behind a seam, and AnyPlay keeps no Discord data

Status: Proposed.

Players want Discord around their games the way a console has it: what they play shows on their Discord profile, friends can join from Discord, Discord friends show beside AnyPlay friends. The launcher already shows a presence over Discord's local IPC pipe, and the portal can link a Discord identity ([ADR 0016](0016-accounts-are-managed-on-the-web.md), [portal API](../../spec/portal-api.md#connections)). Discord's Social SDK (version 1.10.19337 was inspected; it is closed source) does more: presence and invites without a running Discord app, the Discord friend list with live status, and voice and text in lobbies. [The plan](../discord-plan.md) has the order of work; this record has the choices. Five carry it.

**The SDK runs in the net service, loaded at runtime, behind a trait.** The net service is the one process that stays online and holds the player's session ([ADR 0004](0004-net-service-runs-as-its-own-process.md)); it already owns voice and parties, so presence follows the party without a second source of truth. The launcher has no async runtime and a copyleft licence, and shows only what the control protocol reports ([ADR 0006](0006-the-launcher-talks-to-the-net-service-over-its-standard-streams.md)). A crate `crates/discord` holds a trait (`Social`: connect with a token, set the activity, read friends and their status, invite, receive join events) with three implementations: one over the SDK's C API (`cdiscord.h`; the shared library is loaded by `libloading`, the bindings are generated at build time from the header and never committed), one fake that CI and every test use, and an `Off` one. A build without the SDK, or a machine where the library is missing or refuses to load, runs `Off`: the control protocol reports `discord: unavailable` and nothing else changes. The SDK's callbacks are pumped from one thread of their own and only push events into a channel. If the closed library ever proves unstable in-process, the same trait moves to a helper process without touching callers.

**Players link through the SDK's own authorisation, and the cloud exchanges the code but keeps nothing.** The SDK's `Authorize` opens the Discord app's overlay or the browser (redirect `http://127.0.0.1/callback`) and returns a code; the net service sends the code and its PKCE verifier to the cloud, which exchanges it with the client secret (a confidential client, which the SDK's documentation recommends for production) and hands the access and refresh token back to the net service. The same route refreshes. Access tokens last about seven days and a refresh token is replaced at each use. The net service keeps the refresh token in the operating system's credential store, never in a plain file and never in a log; the cloud sees a token only in transit. This keeps the rule of [CONTEXT.md](../../CONTEXT.md) that a connection holds "never a token", and needs no public client: the `Public Client` switch of the Discord application stays off, so no secret is shipped and none is needed. The scopes are `openid sdk.social_layer_presence` plus `identify`, which phases 1 and 2 need; `sdk.social_layer` (voice, text, lobbies, invite messages) is asked only when a phase needs it, as the documentation advises. The identity that comes back must match the account's connection, or create it when the session is fresh, so there is one connection per provider and the portal shows it. The portal's own link (scope `identify`, token dropped) stays as it is, for players who only want their profile to show Discord.

**No provisional accounts.** A provisional account is a Discord account that a game creates for a player who has none, so voice and messages work for everybody. AnyPlay has accounts of its own, and its own friends, messages and party voice, which work without Discord. The bot-token route would send an identity for every AnyPlay account, teenagers' included ([ADR 0012](0012-private-by-default.md)), to Discord whether they want it or not. Discord features exist for players who connected Discord, and for nobody else.

**AnyPlay keeps no Discord data; Discord friends are shown, never copied.** The friend list, the friends' names and pictures, presence and messages live in the net service's memory, go to the launcher as events for the screen, and are dropped when the player disconnects or the session ends. The cloud stores no Discord friend, no list of Discord IDs it received, and no token. This is also Discord's rule: for the minimum feature set the documentation says games "should never copy and store Discord friend information", and Section 5(a)(ii) of the Social SDK Terms limits what may be processed about people who have not linked. To merge the two lists the net service gets from the cloud only the Discord IDs that AnyPlay friends have made visible to friends (a connection's visibility already does this) and compares them locally. Connecting is opt-in, with a screen of our own before the SDK's; presence on Discord is a toggle, on after connecting, and a party set to private shows no party and no join secret. Under-13s cannot use the integrations (Terms, Section 3.b); until a lawyer has looked at the age of consent for this, the Connect button is offered to accounts of 16 and older only.

**The binary is never in a repository; releases carry it as part of the launcher.** The Terms license "to distribute the Discord Social SDK as integrated into your Application" and forbid copying, reproducing or redistributing it otherwise (Section 2). So the library ships inside the launcher's release archive, next to the net service, with Discord's notices, and in no repository. The release workflow fetches a pinned archive (SHA-256 in the workflow) from a private place only the operator can fill, with a read-only token held as a protected secret ([the plan](../discord-plan.md#licensing-and-distribution)); pull requests and forks build against the fake. The files are only those of the platforms we ship: Windows x64 and ARM64, Linux x86-64 (Discord calls Linux experimental), macOS (a universal library). Krisp noise cancellation and its models stay out until voice needs them.

## What the SDK cannot do

- It cannot join a player's Discord server channel or a call in a Discord DM. Its voice exists only in a **lobby** that a game makes, and only SDK clients are in it; the Discord app is not. "Join my Discord voice from the game", as a console does it, is therefore not available through the SDK, and Discord's local RPC voice commands are closed to apps without Discord's approval. What AnyPlay can offer is an "Open Discord" button beside the voice setting (phase 3a), or its party voice carried over a Discord lobby for players who connected (phase 3b).
- It shows only this application's activity of a friend, not their other games.
- Text and voice (lobbies, DMs, linked channels, invite messages) stay under a development cap per application, not per player: 100 lobby creates or joins, 100 lobby updates, 100 direct messages and 100 lobby messages every two hours, and 20 channel links. Production needs Discord's approval, which asks for account linking, presence with joins and a full Discord friend list first, a video of the integration and a statement on protecting age-restricted users. Presence, invites without a message, and the friend list are not capped.

## Consequences

- Phases 1 and 2 (presence, join, unified friends list) cost nothing and need no approval. Phase 3b and any text feature wait for Discord's approval and may be refused, because AnyPlay is a launcher and a network and the review is written for games.
- The Discord application of the SDK is not the AnyPS5 application the IPC presence uses today. While a player is connected the SDK sets the activity and the IPC presence is off, or Discord shows two. Players who do not connect keep the IPC presence, which needs no consent.
- In the glossary a **Connection** stays the portal's link; the net service's signed-in state with Discord is a **Discord session**.
- The launcher's licence is not touched: it neither links nor ships SDK code in its own binary, only the library next to the net service.
- Every SDK update is a decision: Discord may require a newer version (Terms, Section 4.b), the digest is pinned, and an update is a pull request that changes the digest and passes the manual two-account check.
- Discord's rules apply to the interface: the Discord logo unchanged, the display name rather than the username, a Discord badge on friends who are online elsewhere, the entry "Discord Social Experience" for the SDK's settings, and Discord's strings at connection points. The plan lists them.

## Considered options

- **The SDK in the launcher:** the launcher would have to pump the callbacks, carry the closed library in the process of a copyleft program, and could not follow the party. Rejected.
- **A helper process of its own for the SDK:** isolates a crash of the closed code and keeps the licence boundary clean, at the price of one more process to start, watch and update. Kept as the fallback behind the same trait.
- **A public client and the SDK's `GetToken`:** no cloud route, but the application then allows token exchange without a secret, which the documentation advises most games against. Rejected.
- **The cloud keeps the refresh token and hands out short-lived tokens:** fewer re-links after a lost credential store, but the cloud would hold a standing credential for every connected player, against the rule that a connection holds none, and each such token reaches the player's Discord friend list. Rejected.
- **Replace the IPC presence for everybody:** simpler, but players who never connect would lose the presence they have, and the SDK's presence needs a connection.
- **Provisional accounts for every AnyPlay account:** see above.
- **Direct messages and linked channels in the first release:** AnyPlay has its own messages, request inbox, restrictions and moderation ([ADR 0011](0011-messages-are-stored-to-be-delivered.md), [ADR 0012](0012-private-by-default.md)), which a Discord DM would bypass, and the SDK gives a DM history of 72 hours and 200 messages. A Discord friend is messaged in Discord: the friend's row opens the conversation there. Linked channels bridge a lobby with a server's text channel and show a private channel to everybody in the lobby; they may come with groups, not before.
